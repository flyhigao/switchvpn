# 调研笔记：如何让“打开 App 就自动开启 v2rayNG 的代理”

> 结论：**v2rayNG 有现成的对外 API**（官方 Tasker/Locale 插件广播），不需要 root、不需要改 v2rayNG。
> `../activateVpn`（打开即开启）和 `../deactivateVpn`（打开即关闭）就是把这两个 API 各包成一个小 App，已在 OnePlus PJZ110（Android 17，v2rayNG 2.3.14）上实测通过。两者共用 `com/local/vpncommon/Controller.java`。

## 1. 为什么 v2rayNG 打开后代理不会自动开

v2rayNG（2.3.x）没有任何“打开应用就自动连接”的选项。能把代理起来的入口只有：

| 入口 | 说明 | 能否被外部程序调用 |
| --- | --- | --- |
| 主界面那个 V 按钮 / 列表里点服务器 | 需要人手点 | ❌ |
| 快捷方式 `ScStartActivity` / `ScStopActivity` / `ScSwitchActivity`（长按图标→“启动服务”） | 桌面快捷方式，`android:exported="false"`（`app/src/main/AndroidManifest.xml:172-181`） | ❌ 外部 App 起不了 |
| 通知栏磁贴 `QSTileService` | 需要 `android.permission.BIND_QUICK_SETTINGS_TILE` 权限 | ❌ |
| 桌面小部件 `WidgetProvider`（action `com.v2ray.ang.action.widget.click`） | **toggle** 语义：在运行就停，不在运行就开 | ✅ 但“切换”会误关 |
| **Tasker/Locale 插件广播 `TaskerReceiver`** | `android:exported="true"`，`app/src/main/AndroidManifest.xml:328-334` | ✅ 官方设计就是给外部用的 |
| BootReceiver | 开机自启，受设置里“开机启动”开关控制 | ❌ 与 WiFi 无关 |
| 服务 `<pkg>.action.service` + `key=4`（MSG_STATE_STOP） | 运行时动态注册的 receiver，用来停 | ✅ 只能停不能查 |

## 2. 官方 API 的准确用法（v2rayNG 2.3.14 源码）

`app/src/main/java/com/v2ray/ang/receiver/TaskerReceiver.kt`：

```kotlin
val bundle = intent?.getBundleExtra(AppConfig.TASKER_EXTRA_BUNDLE)
val switch = bundle?.getBoolean(AppConfig.TASKER_EXTRA_BUNDLE_SWITCH, false)
val guid   = bundle?.getString(AppConfig.TASKER_EXTRA_BUNDLE_GUID).orEmpty()
if (switch == null || TextUtils.isEmpty(guid)) return
else if (switch) {
    if (guid == AppConfig.TASKER_DEFAULT_GUID) LauncherManager.startServiceFromToggle(context)
    else LauncherManager.startService(context, guid)
} else LauncherManager.stopService(context)
```

常量在 `app/src/main/java/com/v2ray/ang/AppConfig.kt:105-109`：

```
TASKER_EXTRA_BUNDLE        = "com.twofortyfouram.locale.intent.extra.BUNDLE"   // 标准 Locale 协议
TASKER_EXTRA_BUNDLE_SWITCH = "tasker_extra_bundle_switch"                    // Boolean
TASKER_EXTRA_BUNDLE_GUID   = "tasker_extra_bundle_guid"                      // String，"Default" = 用当前选中服务器
TASKER_DEFAULT_GUID        = "Default"
```

所以“开代理”= 发一个显式广播：

```
action    : com.twofortyfouram.locale.intent.action.FIRE_SETTING
component : com.v2ray.ang/.receiver.TaskerReceiver
extra     : com.twofortyfouram.locale.intent.extra.BUNDLE = Bundle{
                tasker_extra_bundle_switch = true,
                tasker_extra_bundle_guid   = "Default" }
```

`LauncherManager.startServiceFromToggle`（`app/src/main/java/com/v2ray/ang/core/LauncherManager.kt:24-37`）会检查“是否选中了服务器”，然后 `startContextService()` → 按设置选 VPN / 纯代理 / root 模式 → `ContextCompat.startForegroundService(...)`，异常（含 `ForegroundServiceStartNotAllowedException`）会被 catch 后 toast。

## 3. 三个必须知道的坑

### 3.1 重复启动不是幂等的，会先停后起

`app/src/main/java/com/v2ray/ang/service/CoreVpnService.kt:77-98` 的 `onStartCommand` 无条件 `setupVpnService()`（关掉旧 tun、establish 新 tun），然后 `startService()` → `CoreServiceManager.startCoreLoop()` 在“已在运行”时返回 false → `stopAllService()`。
后果：对**正在运行**的 v2rayNG 再发一次“启动”，会先断流再重建（甚至停掉）。所以必须先判断状态、已在运行就什么都不做。

### 3.2 没有官方“查状态”的接口

`app/src/main/java/com/v2ray/ang/helper/MessageHelper.kt` 的 `messageIntent()` 里写了 `` `package` = AppConfig.ANG_PACKAGE ``，所以 `MSG_REGISTER_CLIENT(1)` 的回包（`<pkg>.action.activity` 里 key=11 运行 / 12 未运行）是**定向发给 v2rayNG 自己**的，第三方 App 收不到。

可行的状态判断（本项目采用）：

1. 连着 `127.0.0.1:10808`（默认 socks 端口）/ `10809`（http 端口）→ 通就是运行中；
2. `ConnectivityManager.getNetworkCapabilities(getActiveNetwork()).hasTransport(TRANSPORT_VPN)` → 自己是全局 VPN 下就是 true。

（若用户改过 v2rayNG 的 socks 端口，第 1 条失效，需要改 `Controller.SOCKS_PORTS`。）

### 3.3 Android 12+ 后台启动前台服务受限

v2rayNG 的 targetSdk 是 37。理论上前台服务不能从后台随便起。实测在 Android 17 上：

- 由**第三方 App 发广播**触发 `startForegroundService` —— 可以成功（v2rayNG 进程处于“正在处理广播”状态）；
- 最保险的兜底是**把 v2rayNG 的界面拉到前台再发一次**（应用可见时一定放行）。本项目实现为第二招。

## 4. 实测记录（OnePlus PJZ110 / Android 17 / v2rayNG 2.3.14 / ColorOS）

| 场景 | 结果 |
| --- | --- |
| 代理已在运行，点 activateVpn | 不做任何事（v2rayNG service 的 createTime 不变，不重启、不断流） |
| 代理已关（widget 广播关掉），点 activateVpn | ~0.3s 起来，无 UI 介入 |
| 代理被 `am force-stop`（自动化“关闭程序”通常等于这个），点 activateVpn | ~0.5s 起来 |
| activateVpn 自己被 force-stop（冷进程），点图标 | ~0.3s 起来 |
| 点 deactivateVpn（代理在运行） | 停止指令生效，端口立刻关闭 |
| 点 deactivateVpn（代理已关） | 报“本来就没在运行”，无副作用 |
| 屏幕熄灭 / Doze 状态下触发 | 正常起来，且不会点亮屏幕（透明 Activity） |
| 只发广播（`com.local.activatevpn.action.ON`）不打开界面 | 能工作，但应用被 ColorOS 冻结（`OplusHansManager ... try idling`）时广播会排队延迟十几秒；**用“打开应用”这条路最可靠** |
| v2rayNG 的 widget 广播（`com.v2ray.ang.action.widget.click`） | 能开能关，但是 toggle，不能用来“确保开启” |

## 5. 备选方案（以及为什么不选）

1. **Tasker / MacroDroid 直接用 v2rayNG 插件**：如果自动化 App 本身支持第三方插件或能发带 Bundle 的广播，可以不装本 App。但国内手机自带的“自动任务/快捷指令”通常只能“打开应用”，发不了带嵌套 Bundle 的广播（`am broadcast` 的 `--ez` 之类只能塞扁平 extra，塞不了嵌套 Bundle），所以还是需要这个 App。
2. **ADB / root**：`adb shell am broadcast ...` 或 root 下 `am start-foreground-service` 都能实现，但要么得连电脑，要么得 root。
3. **改 v2rayNG 源码自己编译一版**：可行但维护成本高，且作者明确提供了 Tasker 接口，没必要。
4. **“Always-on VPN”**：v2rayNG 支持被系统当成 always-on VPN 拉起，但那是开机/断网自愈用的，无法表达“离开家 WiFi 才开”。

## 附：10 秒防抖的调研（2026-11-15 夜间实测）

需求：网络切换瞬间的“短暂离开/连上”不应触发动作，要等 10 秒确认。

试过、不可行的：
- **就地 sleep**（透明 Activity 或前台服务里）：ColorOS 把退到后台的进程直接丢进 freezer（`/sys/fs/cgroup/apps/uid_XXXXX/pid_XXXXX/cgroup.freeze` = `1`，日志 `OplusHansManager : freeze uid: ...`），FGS 也挡不住，worker 线程根本没被创建。
- **AlarmManager 精确闹钟**：`SCHEDULE_EXACT_ALARM` 在 Android 14 新装默认拒绝（`SecurityException: ... needs to hold ... SCHEDULE_EXACT_ALARM or ... USE_EXACT_ALARM`）；加了 `USE_EXACT_ALARM` 能定上，但 `dumpsys alarm` 显示 ColorOS 的 `OplusAlarmAdjustment` 把后台应用闹钟改写成 `adjustment=+2d23h...`。
- **expedited Job 里再 sleep 10 秒**：Job 能立刻跑（19ms），但一 sleep 进程又被冻，`SettleJob start` 之后没有下文。

最终方案：
- `JobScheduler` 排 `setMinimumLatency(10s)` + `setOverrideDeadline(11s)`，到点系统唤醒进程执行 → `SettleJobService.onStartJob` → `Controller.firePending()`。
- 同一进程里再起一个 `vpnswitch-waiter` 线程就地等 10 秒（屏幕亮/未被冻时更准时），先到先做，另一个看到 pending 已清就空转。
- Job 有时会被立刻放行（Activity 刚起时进程算前台），此时 `firePending` 发现 `elapsed < settle` 会把剩余时间再排一次，绝不在 10 秒前动手。
- 每次触发带 nonce，旧 waiter 看到 nonce 不匹配就 `stale waiter ... ignore`，避免“两次触发立刻执行”。
- 到点比对「WiFi 指纹」（`WIFI|<默认网关>`，跳过 VPN transport），变了就放弃。

前提：两个 App 需要「允许完全后台运行」，否则以上定时/等待都会被 ROM 冻结或推迟。
